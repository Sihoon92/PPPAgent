01배경 — 평가라는 말에 섞여 있는 두 개의 질문

"생성된 PPT가 제대로 만들어졌는지 평가한다"는 한 문장처럼 들리지만, 안에는 성격이 전혀 다른 두 질문이 들어 있다.

질문 A 템플릿 충실도 내가 넣으라고 지시한 내용이, 지시한 틀에, 틀을 깨지 않고 들어갔는가?
vs
질문 B 콘텐츠·시각 품질 그렇게 만들어진 슬라이드가 사람이 보기에 좋은가?

둘은 답을 구하는 방식이 근본적으로 다르다. A에는 정답지가 있다. 무슨 텍스트를 넣으라고 시켰는지, 어떤 레이아웃을 골랐는지, 원본 템플릿이 무엇이었는지를 프로그램이 전부 알고 있다. 그러니 A는 문자열 비교와 집합 연산으로 답할 수 있다 — 결정적이고, 재현 가능하고, 모델이 필요 없고, 밀리초 단위로 끝난다.

B에는 정답지가 없다. "이 슬라이드가 보기 좋은가"는 렌더링된 픽셀을 봐야 알 수 있고, 보고 나서도 사람마다 답이 다르다. 그래서 B는 모델에게 물어보는 수밖에 없고, 물어볼 때마다 답이 조금씩 흔들린다.

이 저장소는 두 질문에 서로 다른 시점, 서로 다른 메커니즘으로 대응한다. 그리고 이 문서의 핵심 주장은 이것이다 — A는 "채점"이 아니라 "강제"로 구현되어 있다. 코드 어디에도 "템플릿 충실도 점수"를 계산하는 함수는 없다. 대신 충실도를 어기면 애초에 통과하지 못하게 막는 관문이 파이프라인 곳곳에 박혀 있다.

깊은 배경 — 왜 슬라이드는 "열리는 것"만으로 부족한가 (이미 아신다면 건너뛰세요)

일반적인 코드 생성이라면 "컴파일되면 절반은 성공"이다. 슬라이드는 그렇지 않다. .pptx는 ZIP 안의 XML 묶음이고, python-pptx가 쓴 파일은 문법적으로 거의 항상 유효하다. 파일이 열린다는 사실은 아무것도 보장하지 않는다.

슬라이드에서 실제로 깨지는 것은 문법이 아니라 배치다. 대표적인 실패 세 가지:

  • 넘침(overflow) — 텍스트 상자는 400pt 폭인데 글자가 600pt어치 들어갔다. XML은 완벽하게 유효하고, python-pptx는 아무 불평도 하지 않고, PowerPoint에서 열면 글자가 상자를 뚫고 옆 도형 위로 흘러넘친다. 파일을 다시 파싱하는 방식의 검증으로는 절대 잡히지 않는다.
  • 더미 잔존 — 템플릿 원본의 "Lorem ipsum"이나 예시 문구가 지워지지 않고 남았다. 역시 유효한 파일이다.
  • 참조 파손 — 이미지 관계(relationship)가 끊겨 회색 X 상자가 뜬다.

셋 다 "파일이 유효한가"라는 질문으로는 통과한다. 그래서 슬라이드 검증은 파일 검증이 아니라 의미 검증이어야 하고, 그게 이 문서 전체의 배경이다.

02직관 — 문지기와 심판

비유 하나로 전체 구조를 잡고 가자. 슬라이드 하나가 만들어지는 길은 복도다. 복도에는 문지기(gate)가 여럿 서 있고, 복도 끝에는 심판(judge)이 앉아 있다.

문지기는 조건이 안 맞으면 그 자리에서 되돌려 보낸다. 점수를 매기지 않는다. 통과 아니면 반송이다. 심판은 이미 만들어져 나온 결과물에 1점에서 5점까지 점수를 붙인다. 되돌려 보내지는 않는다.

핵심 개념 — 강제(enforcement)와 측정(measurement)은 다르다

문지기는 나쁜 것이 나오지 못하게 한다. 심판은 나온 것이 얼마나 좋은지 말한다. 이 저장소의 템플릿 충실도는 100% 전자다. 그래서 "이 덱의 충실도 점수는 몇 점인가"라고 물으면 답할 코드가 없다 — 대신 "이 덱은 문지기 다섯을 전부 통과했다"만 말할 수 있다. 문지기가 못 보는 실패는 영원히 보이지 않는다는 뜻이기도 하다. 7절에서 이 문제로 돌아온다.

질문 메모 위 복도 그림에서 헷갈리는 지점이 있다면 적어두세요.

문지기 1 — 요소 계약: 같은 일을 하는 두 개의 다른 구현

가장 기본적인 검사다. 레이아웃이 요구하는 요소 집합과 모델이 준 요소 집합이 일치하는가? 그런데 이 저장소에는 이 검사가 두 벌 있다. 실행 경로가 둘이기 때문이다.

파이프라인 경로 — Layout.validate() layout.py:76

def validate(self, editor_output: EditorOutput, allowed_images: list[str]):
    for el in self.elements:
        if el.name not in editor_output:
            raise ValueError(f"Element {el.name} not found in editor output")
        if self[el.name].type != "image":
            continue
        # ↓ 이미지 경로는 "정확히 존재하는가"가 아니라 "가장 비슷한 게 있는가"로 판정
        sim_image = max(
            allowed_images,
            key=lambda x: edit_distance(x, editor_output[el.name].data[i]),
        )
        if edit_distance(sim_image, editor_output[el.name].data[i]) < 0.5 or not exists(sim_image):
            raise ValueError(f"Image ... not found")
        editor_output[el.name].data[i] = sim_image  # 조용히 교정한다

마지막 줄이 눈여겨볼 지점이다. 모델이 /work/media/revenue_chart.png를 /work/media/revenue-chart.png로 잘못 썼다고 하자. 정규화 편집거리 (utils.py:233, 1 - Levenshtein/max_len)가 0.5 이상이면 가장 비슷한 실제 파일로 경로를 덮어쓴다. 오류가 아니라 자동 교정이다. LLM이 파일명을 조금 틀리는 건 흔한 일이니 실용적인 선택이다.

MCP 경로 — mcp_slide_validate() mcp_server.py:32

def mcp_slide_validate(editor_output, layout, prs_lang):
    warnings, errors = [], []
    length_factor = get_length_factor(prs_lang, Language.english())
    layout_elements = {el.name for el in layout.elements}
    editor_elements = {el.name for el in editor_output.elements}
    for el in layout_elements - editor_elements:
        errors.append(f"Element {el} not found in editor output")   # 누락
    for el in editor_elements - layout_elements:
        errors.append(f"Element {el} not found in layout")          # 잉여
    if errors:
        # 아래 길이 검사는 레이아웃 요소명으로 editor_output을 인덱싱한다.
        # 지금 반환하지 않으면 KeyError 가 위 에러들을 덮어버린다.
        return warnings, errors
    for el in layout.elements:
        if layout[el.name].type == "image":
            for i in range(len(editor_output[el.name].data)):
                if not exists(editor_output[el.name].data[i]):   # 정확 일치
                    errors.append(f"Image ... not found")

                warnings.append(f"Element {el.name} has {charater_counts} characters, ...")
    return warnings, errors

차이가 셋이다. 첫째, MCP 쪽은 양방향 집합 차를 본다 — 누락뿐 아니라 레이아웃에 없는 요소를 넣은 경우도 잡는다. 파이프라인 쪽은 누락만 본다. 둘째, 이미지는 퍼지 매칭 없이 exists()다. 경로가 한 글자만 틀려도 실패한다. 셋째 — 그리고 이게 가장 중요한데 — 길이 계수가 다르다.

같은 검사, 두 벌의 구현

이건 중복이 아니라 정책 분기다. 파이프라인은 source_doc에서 허용 이미지 목록을 끌어올 수 있어 퍼지 교정이 가능하지만, MCP 서버는 모델이 임의 경로를 주는 열린 환경이라 교정할 후보 목록 자체가 없다. 그래서 정확 일치로 갈 수밖에 없다. 다만 두 구현이 어긋나 있다는 사실 자체는 유지보수 부담이고, 실제로 다음 절의 버그를 낳았다.

문지기 2 — 길이 예산: 한글 40자는 영어 42자가 아니다

여기가 템플릿 충실도의 가장 미묘하고 가장 중요한 부분이다. 템플릿 슬라이드의 텍스트 상자는 고정 크기고, 그 안에 몇 글자가 들어가는지는 글자 폭에 달렸다. 그런데 CJK 글자는 라틴 글자보다 대략 두 배 넓다.

suggested_characters는 어디서 왔는가? Element.model_post_init (layout.py:29)에서 템플릿 원본 슬라이드에 실제로 들어 있던 텍스트의 최대 길이로 자동 계산된다. 

def model_post_init(self, _):
    if self.type == "text":
        self.suggested_characters = max(len(i) for i in self.data)

즉 영어 템플릿이면 42는 "영어 42자가 들어가던 상자"라는 뜻이다. 여기에 언어 변환 계수를 곱한다. 

# pptgen.py:39
def get_length_factor(src_lan: Language, dst_lang: Language):
    if src_lan.latin == dst_lang.latin:  # 같은 어족 — 여유를 조금 준다
        return 1.2
    elif src_lan.latin:                  # 라틴 → CJK: 글자가 넓으니 예산을 줄인다
        return 0.7
    else:                                # CJK → 라틴: 글자가 좁으니 예산을 늘린다
        return 2.0

Language.cjk는 lid in ["zh","ja","ko"]로 판정한다(utils.py:43). 이제 두 경로가 같은 예제에서 다른 답을 내는 장면을 보자.

중요한 결과 — MCP 경로는 CJK 출력에 대해 예산을 1.7배 과대 책정한다

파이프라인은 generate_pres(dst_language=...)에서 출력 언어를 받아 get_length_factor(reference_lang, dst_lang)를 계산한다(pptgen.py:176-177). MCP 서버에는 그런 매개변수가 없다. write_slide는 요소 배열만 받는다. 그래서 영어 템플릿 + 한국어 출력이면 예산이 42×0.7=30이어야 하는데 42×1.2=51이 적용된다 — 1.7배 관대하다. 중국어 템플릿이었다면 (zh→en)=2.0이 걸려 84자까지 통과한다.

이건 오타 수준의 실수가 아니라 구조적 공백이다. MCP 흐름에 출력 언어를 선언할 자리가 없다. 고치려면 set_template이나 write_slide에 언어 인자를 추가해야 한다.

경고가 나면 무슨 일이 일어나는가 — 두 경로가 또 갈린다

1단계 — 왜 이미지를 바로 채점하지 않는가

이제 슬라이드 그림이 있다. 가장 단순한 접근은 "이 슬라이드 몇 점?"이라고 VLM에게 그림을 던지는 것이다. ppteval은 그렇게 하지 않는다. 두 단계로 쪼갠다.

왜 이렇게 나눴을까? 이유가 셋이다.

이유설명
재현성 루브릭 적용이 순수 텍스트 추론이 된다. 멀티모달 추론은 같은 이미지에도 답이 크게 흔들리지만, 같은 서술 문장에 같은 5점 루브릭을 적용하는 일은 훨씬 안정적이다.
캐시 가능성 서술은 슬라이드마다 slide_03.json에 저장된다(ppteval.py:63-69). 루브릭을 고쳐 재채점할 때 비싼 VLM 호출을 다시 하지 않는다.
감사 가능성 점수가 이상할 때 "무엇을 보고 그렇게 판단했는지"가 파일로 남아 있다. 점수만 있는 시스템은 디버깅이 불가능하다.

대가는 명확하다. 모델 호출이 슬라이드당 2배이고(서술 1 + 채점 1, 그것도 style·content 각각이므로 총 4회), 서술 단계가 놓친 정보는 채점 단계에서 영영 복구되지 않는다.

ppteval_style.txt와 ppteval_content.txt는 둘 다 상단에 "Each score level requires that all evaluation criteria meet the standards of that level"이라고 못 박는다. 즉 연속적인 가중합이 아니라 단계 통과식이다. 위 예제에서 겹침 하나가 나오면 1점 기준("스타일 충돌로 내용을 읽기 어렵다")에 걸려 배색이 아무리 좋아도 1점이다.

두 장이 여기서 만난다

3장에서 본 실패 C(텍스트 넘침)는 문지기 어느 누구도 잡지 못했다. 그런데 그 슬라이드를 렌더링하면 VLM 서술에 "overlapping elements"가 등장하고, 그 순간 style 점수는 1점으로 떨어진다.

시각 품질 채점이 템플릿 충실도 실패를 간접적으로 잡아낸다. 다만 간접적이라는 게 문제다 — 점수가 1점이라는 사실만으로는 "넘쳤다"인지 "배색이 충돌한다"인지 알 수 없고, reason 필드를 사람이 읽어야 구분된다. 자동 회귀 게이트로 쓸 수 없는 이유다.

def verify(self, pdf_file: Path, text: str) -> float:
    reader = PdfReader(str(pdf_file)); result = []

    # ① 페이지 수가 요청 범위 안인가
    if self.page_low and self.page_high:
        result.append(self.page_low <= len(reader.pages) <= self.page_high)

    # ② 화면비가 맞는가 — PDF mediabox 를 직접 잰다
    if self.aspect_ratio:
        ar_map = {WIDE_SCREEN: 16/9, STANDARD_SCREEN: 4/3, POSTER: 594/841}
        actual_ar = float(reader.pages[0].mediabox.width / reader.pages[0].mediabox.height)
        result.append(abs(actual_ar - ar_map[self.aspect_ratio]) < 0.1)

    # ③ 출력 언어가 맞는가 — fastText 언어식별
    language = lid_model.predict(text[:1024].replace("\n", ""))[0][0]
    result.append(self.language == language.replace("__label__", ""))

    return sum(result) / len(result)   # 불리언이 아니라 "만족 비율" 0~1

반환값이 통과/실패가 아니라 비율인 게 핵심이다. 세 제약 중 둘을 만족하면 0.67이다. 그래서 나중에 다른 점수들과 나란히 평균 낼 수 있다 — 다만 척도가 달라서 보정이 필요하고, 그 보정이 log_scores에 숨어 있다(다음 장).

def vendi_score(features):
    features = features / np.linalg.norm(features, axis=1, keepdims=True)
    similarity  = features @ features.T                   # 코사인 유사도 행렬
    eigenvalues = np.linalg.eigvalsh(similarity); eigenvalues = np.clip(eigenvalues, 0, None)
    eigenvalues = eigenvalues / eigenvalues.sum()
    entropy = -np.sum(eigenvalues * np.log(eigenvalues))
    return float(np.exp(entropy))                         # 유사도 행렬 고유값의 엔트로피 지수

def evaluate(self, task_slides):
    vs = vendi_score(self._extract_all_features(task_slides))
    return float(np.log(vs) / np.log(len(features)))       # [0, 1] 로 정규화

직관은 간단하다. Vendi Score는 "실질적으로 서로 다른 덱이 몇 개인가"를 세는 지표다. 덱이 n개일 때 범위는 1(전부 동일)에서 n(전부 최대한 다름)이고, log(VS)/log(n)으로 나누면 0~1이 된다.

상황 (덱 3개)유사도 행렬Vendi Score정규화 결과
전부 시각적으로 동일모든 원소 ≈ 1≈ 1log(1)/log(3) = 0.00
둘은 비슷, 하나만 다름부분적 블록 구조≈ 2log(2)/log(3) ≈ 0.63
셋 다 서로 무관단위행렬에 가까움≈ 3log(3)/log(3) = 1.00
이 지표가 재지 않는 것

덱 하나를 벡터 하나로 평균내기 때문에(features.mean(dim=0)), 한 덱 안에서 같은 레이아웃만 20장 반복하는 문제는 이 지표로 전혀 보이지 않는다. 평균을 내면 그 단조로움이 사라진다. 덱 간 다양성이지 덱 내 다양성이 아니다.

질문 메모 Vendi Score나 DINOv2 부분에서 막히면 여기에 적어두세요.

constraint는 경계에 있다. 결정적이므로 게이트로 쓸 수 있지만, 반환값이 불리언이 아니라 비율(0~1)이라 임계값을 정해야 한다.

08퀴즈

읽은 내용이 실제로 남았는지 확인해 보자. 다섯 문제 모두 코드의 구체적인 동작을 묻는다.

1. MCP 경로에서 영어 템플릿으로 한국어 슬라이드를 만들 때, mcp_slide_validate가 적용하는 글자수 예산은?

아깝다. 0.7은 올바른 값이지만 실제로 적용되는 값이 아니다. 파이프라인 경로(generate_pres(dst_language=...))라면 0.7이 맞다. 정확하다. get_length_factor(prs_lang, Language.english())로 두 번째 인자가 영어로 고정돼 있다. 템플릿이 영어면 (en, en) → src.latin == dst.latin → 1.2. 한글에는 1.7배 관대한 예산이다. 2.0은 CJK 템플릿에서 나오는 값이다. 중국어 템플릿이었다면 (zh → en)이 되어 2.0이 걸린다. 그럴 것 같지만 아니다. MCP 흐름에는 출력 언어를 선언할 자리 자체가 없다 — write_slide는 요소 배열만 받는다.

2. Presentation.validate()가 실제로 하는 일은?

이름 때문에 그렇게 읽히지만 아니다. 이 함수는 아무것도 판정하지 않고 아무것도 반환하지 않는다(빌드된 슬라이드만 반환). 맞다. 이름은 validate지만 하는 일은 정리다. 모델이 손대지 않은 템플릿 문단에 del_para 클로저를 달아 XML에서 제거한다 — 더미 문구 잔존을 막는 유일한 장치다. 품질 채점은 ppteval의 일이고, 이 함수는 모델을 전혀 쓰지 않는다. 이미지 경로 확인은 Layout.validate와 mcp_slide_validate가 편집 전에 한다.

3. ppteval이 슬라이드 이미지를 VLM에 넣어 바로 점수를 받지 않고 "서술 → 채점" 2단계를 쓰는 가장 큰 이유는?

오히려 반대다. 슬라이드 한 장에 VLM 2회 + LLM 2회로 호출이 늘어난다. 비용은 이 설계가 지불하는 대가지 이득이 아니다. 정확하다. 루브릭 적용이 순수 텍스트 추론이 되어 흔들림이 줄고, 서술은 slide_03.json에 저장되므로 루브릭을 고쳐 재채점할 때 비싼 VLM 호출을 건너뛴다. 덤으로 "무엇을 보고 그렇게 판단했는지"가 파일로 남아 감사가 가능하다. 두 단계 모두 return_json=True로 JSON을 요구한다. 형식 문제가 아니다. ppt_to_images(dpi=100)는 채점에 충분한 해상도다. 해상도는 이 설계의 동기가 아니다.

4. DataPoint.verify()가 반환하는 값의 형태는?

불리언을 모으긴 하지만 그대로 반환하지 않는다. all()이 아니라 평균이다. 맞다. return sum(result) / len(result) — 세 제약 중 둘을 만족하면 0.67이다. 그래서 log_scores에서 score *= 5로 다른 1~5 지표와 척도를 맞춘다. 1~5는 style/content/coherence의 척도다. constraint는 0~1이고, 비교하려면 5를 곱해야 한다. 위반 목록을 반환하는 구조(ConstraintEvalResult)가 typings.py에 정의돼는 있지만 채워지지 않는다.

5. 시각적으로 완전히 동일한 덱 3개를 SlideStyleDiversity.evaluate()에 넣으면?

맞다. 모두 동일하면 유사도 행렬의 원소가 전부 1이라 고유값 하나에 질량이 몰리고 엔트로피가 0, 따라서 VS = exp(0) = 1. 정규화하면 log(1)/log(3) = 0이다. 1.0은 정규화 전 Vendi Score 값이다. 반환값은 log(VS)/log(n)이므로 한 번 더 변환된다. 3.0은 세 덱이 서로 완전히 무관할 때의 Vendi Score(=n)다. 정규화하면 1.0이 된다. 분모가 log(n)이라 결과는 항상 0~1 범위다. 1.10 같은 값은 나올 수 없다.
