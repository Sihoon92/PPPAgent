01배경 — MCP라는 배선

원본 문서를 끝까지 읽었다면 set_template, create_slide, write_slide 같은 이름이 눈에 익을 것이다. 하지만 거기서는 그 함수들이 “어딘가에서 호출된다”는 정도로만 다뤘다. 실제로는 그 함수들이 다른 프로세스에 살고 있고, 그 프로세스와 대화하는 규약이 MCP다.

아주 기초부터: 도구 호출과 MCP가 뭔가요? (이미 아신다면 건너뛰세요)

언어 모델은 글자만 뱉는다. 파일을 읽지도, 파워포인트를 저장하지도 못한다. 그래서 요즘 모델에는 도구 호출(tool call)이라는 우회로가 있다. 모델에게 “네가 쓸 수 있는 함수 목록은 이거다”라고 스펙을 함께 주면, 모델은 답변 대신 {"name": "read_file", "arguments": {"path": "a.md"}} 같은 JSON을 뱉는다. 그 JSON을 받아 진짜 함수를 실행하고 결과를 다시 모델에게 돌려주는 건 프로그램의 몫이다. 모델은 끝까지 글자만 다룰 뿐이다.

MCP(Model Context Protocol)는 “그 진짜 함수들을 어디에 두고 어떻게 부를 것인가”에 대한 표준이다. 함수를 호스트 프로그램 안에 박아 넣는 대신 독립된 프로세스(MCP 서버)로 띄우고, 표준입출력이나 HTTP로 JSON-RPC 대화를 나눈다. 이렇게 하면 (1) 도구 묶음을 언어·런타임에 관계없이 갈아끼울 수 있고, (2) 위험한 도구를 컨테이너 안에 가둘 수 있고, (3) 같은 도구 서버를 여러 호스트가 재사용할 수 있다.

이 저장소에서 “서버”라는 말은 웹 서버가 아니라 자식 프로세스를 뜻한다는 점만 기억하면 된다. 대부분 python3 어떤파일.py로 뜨고, 하나는 docker run으로 뜬다.

이 저장소가 띄우는 MCP 서버 일곱 개

목록은 deeppresenter/mcp.json에 있고, 템플릿은 deeppresenter/mcp.json.example이다. 실행 시 AgentEnv가 이 파일을 읽어 서버를 전부 띄운 뒤, 각 서버에게 “너는 어떤 도구를 갖고 있니”(list_tools)를 물어 도구 카탈로그를 만든다 (deeppresenter/agents/env.py:298-323).

서버실행 방식도구역할
sandbox docker run … deeppresenter-sandbox read_file, write_file, move_file, edit_file, create_directory, list_directory, execute_command 격리된 파일시스템/셸
pptagent pptagent-mcp list_templates, set_template, create_slide, write_slide, generate_slide, save_generated_slides, markdown_table_to_image 템플릿 기반 슬라이드 생성
task python3 tools/task.py finalize 루프 종료 + 결과물 검증
any2markdown python3 tools/any2markdown.py convert_to_markdown PDF·오피스 문서 → 마크다운
search python3 tools/search.py 웹 검색 계열 네트워크 필요 (offline_mode면 제외)
tool_agents python3 tools/tool_agents.py image_caption LLM 기반 보조 도구
deeppresenter python3 tools/reflect.py inspect_slide, inspect_manuscript 산출물 자기 점검

서버 이름이 deeppresenter인 것과 패키지 이름이 deeppresenter인 것, 서버 이름이 pptagent인 것과 CLI 명령이 pptagent인 것이 겹쳐서 헷갈리기 쉽다. 이 글에서 등폭 글꼴로 쓴 pptagent는 언제나 MCP 서버 하나를 가리킨다.

02직관 — 같은 도구 상자를 역할마다 다르게 채운다

서버 일곱 개가 떠 있다고 해서 모든 에이전트가 그 도구를 다 쓰는 건 아니다. 이 시스템의 핵심 설계는 놀랄 만큼 단순하다.

한 문장 요약

도구는 공용 창고에 한 번만 로드하고, 역할(role)마다 그 창고에서 꺼내 쓸 목록을 YAML로 다르게 정한다. 같은 프로세스, 같은 연결, 다른 도구 목록.

비유하자면 공구 창고 하나에 망치·드라이버·용접기·전동톱을 다 넣어두고, 목수에게는 망치와 드라이버만 든 벨트를 채워주고, 용접공에게는 용접기만 채워주는 식이다. 창고를 두 개 만들 필요도, 목수에게 용접기를 안 쓰겠다는 약속을 받을 필요도 없다. 애초에 손에 쥐어주지 않는다.

실제 코드에서 이 “벨트 채우기”는 _setup_toolset() 한 함수다 (deeppresenter/agents/agent.py:138-156). YAML의 네 필드를 읽어 도구 목록을 조립하고, 그 목록만 LLM에게 스펙으로 넘긴다.

Research 역할

roles/Research.yaml · use_model: research_agent
toolset:
  include_tool_servers: all
  exclude_tool_servers:
    - pptagent
  exclude_tools:
    - inspect_slide
search any2markdown tool_agents sandbox task deeppresenter pptagent

조사·수집 단계. 슬라이드를 만들 도구는 일부러 손에 쥐어주지 않는다.

PPTAgent 역할

roles/PPTAgent.yaml · use_model: research_agent
toolset:
  include_tool_servers:
    - pptagent
    - sandbox
  include_tools:
    - finalize
pptagent sandbox finalize search any2markdown tool_agents deeppresenter

제작 단계. 딱 7 + 7 + 1 = 15개 도구만 보인다. include_tools는 서버 단위가 아니라 도구 하나만 집어오는 통로다.

Research가 pptagent를 제외하는 진짜 이유

단순히 “필요 없어서”가 아니다. pptagent 서버는 상태를 들고 있는(stateful) 서버다. set_template()로 로드한 템플릿 컨텍스트와 지금까지 쌓인 슬라이드 목록이 서버 프로세스 메모리에 그대로 남아 있다. 조사 단계 에이전트가 호기심에 set_template을 한 번 부르면 그때까지 쌓인 슬라이드가 전부 날아간다 (pptagent/mcp_server.py:197의 self.slides.clear()). 격리는 예의가 아니라 안전장치다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

03아키텍처 — 프로세스는 몇 개나 뜨는가

한 번의 생성을 실행하면 실제로 여덟 개의 프로세스가 뜬다. 호스트 하나, 서버 일곱. 그중 하나는 도커 컨테이너다. 아래가 그 전체 그림이다.

PPTAgent 역할이 쓰는 서버 떠 있지만 이 역할에는 안 보이는 서버 호스트 프로세스

서버는 어떻게 자기 워크스페이스를 알게 되는가

mcp.json의 args와 env에는 $PACKAGE_DIR, $WORKSPACE, $HOST_WORKSPACE, $WORKSPACE_ID, $CONFIG_FILE 같은 자리표시자가 들어 있다. 이걸 실제 값으로 바꾸는 건 MCPServer._process_escape()다 (deeppresenter/utils/typings.py:35-60). 값은 AgentEnv.__init__에서 만들어진다 (deeppresenter/agents/env.py:86-94). 

envs = {
    "WORKSPACE":      str(self.workspace),        # ~/.cache/deeppresenter/<session>
    "HOST_WORKSPACE": host_workspace,             # 도커-in-도커일 때 호스트 쪽 실제 경로
    "WORKSPACE_ID":   self.workspace.stem,        # 컨테이너 이름으로 재사용
    "CONFIG_FILE":    str(config.file_path),      # 서버가 모델 설정을 다시 읽을 수 있게
    "PACKAGE_DIR":    str(PACKAGE_DIR),
}
WORKSPACE와 HOST_WORKSPACE가 따로 있는 이유

도커 컴포즈로 띄우면 호스트 프로세스 자체가 컨테이너 안에 있다. 그 안에서 다시 docker run -v A:B를 실행하면, 볼륨 경로 A는 컨테이너 안 경로가 아니라 진짜 호스트의 경로여야 한다. DEEPPRESENTER_HOST_WORKSPACE_BASE가 설정돼 있으면 그 값으로 경로를 되매핑한다. 로컬 개발에서는 둘이 같은 값이다.

질문 메모 프로세스 그림에서 헷갈리는 부분을 적어두세요.

04워크플로 — 한 번의 생성에서 벌어지는 일

전체 파이프라인은 두 단계다. Research가 원고 마크다운을 만들고, PPTAgent가 그 마크다운을 슬라이드로 옮긴다 (deeppresenter/main.py:112-168). 두 단계는 하나의 AgentEnv를 공유하되, 앞서 본 대로 손에 쥐는 도구가 다르다.

stage 1Research search / any2markdown / sandbox 사용
→ manuscript.md
→
gatefinalize(agent_name="Research") .md 확장자 확인 + 이미지 링크 절대경로 재작성
→
stage 2PPTAgent pptagent / sandbox 사용
→ deck.pptx

아래가 2단계의 실제 대화다. 화살표 하나가 곧 JSON-RPC 왕복 한 번이고, 점선은 되돌아오는 응답이다. 예시 값은 “ICIP 발표자료를 thu 템플릿으로 10장” 요청을 가정했다.

실선 = 도구 호출, 점선 = 응답. 굵은 화살표 하나가 stdio JSON-RPC 왕복 한 번이다. generate_slide에만 자기 자신을 향한 화살표가 붙어 있는데, 그 안에서 또 다른 LLM 호출이 일어나기 때문이다 (7장에서 자세히).
한 턴에 도구 7개까지

LLM이 한 번의 응답에서 요청할 수 있는 도구 호출은 MAX_TOOLCALL_PER_TURN = 7로 제한된다 (deeppresenter/utils/constants.py:16). 초과하면 execute()가 어서션 실패를 도구 결과 메시지로 되돌려준다 — 예외로 죽는 게 아니라 모델에게 “너무 많이 불렀다”고 알려주고 다시 시도하게 한다 (deeppresenter/agents/agent.py:261-287).

질문 메모 시퀀스 다이어그램에서 이해가 안 되는 단계를 적어두세요.

05pptagent 서버는 상태 기계다

pptagent 서버의 도구 일곱 개는 아무 순서로나 부를 수 있는 독립 함수가 아니다. 각 도구가 시작하자마자 assert로 선행 조건을 확인하는데, 그 어서션들을 모아 보면 정확히 하나의 상태 기계가 나온다. 이걸 그림으로 보면 이 서버의 설계 의도가 한눈에 들어온다.

초록 실선 = 정상 전이, 빨간 점선 = 어서션 실패로 되돌아오는 에러. 에러는 예외가 되어 도구 결과로 전달되고, LLM은 그 문장을 읽고 스스로 순서를 고친다.

도구별 입력과 출력

도구입력출력왜 이 모양인가
list_templates 없음 {message, templates:[{name, description}]} 각 템플릿의 description.txt를 그대로 실어 보낸다. 모델이 주제에 맞는 걸 고를 근거가 된다.
set_template template_name: str {template_description, available_layouts:[…]} source.pptx + slide_induction.json을 메모리에 올린다. 누적 슬라이드를 지우므로 1회만.
create_slide layout: str {instructions, schema} 레이아웃의 content_schema — 요소 이름·타입·권장 글자수·기본 개수를 사람이 읽는 평문으로.
write_slide [{name, data:[str]}] {message} / {warnings:[…]} / 예외 검증 게이트. 이름 불일치·이미지 부재는 예외, 길이 초과는 경고. 실패 대신 협상.
generate_slide 없음 (서버 상태 사용) {message, available_layouts} 내부에서 coder LLM이 편집 코드를 만들어 템플릿 슬라이드 사본에 실행. 반환된 레이아웃 목록은 매번 섞여서 온다.
save_generated_slides pptx_path: str 저장 확인 문자열 누적 슬라이드를 하나의 pptx로 직렬화하고 상태를 초기화한다.
markdown_table_to_image markdown_table, path, css 저장된 이미지 경로 템플릿 도형에는 마크다운 표를 넣을 수 없다. 표를 그려서 이미지 요소로 우회한다.
왜 generate_slide는 레이아웃 목록을 매번 섞어서 돌려줄까

shuffle(available_layouts)가 코드에 그냥 들어 있다 (pptagent/mcp_server.py:299). 목록 순서가 고정이면 LLM이 앞쪽 레이아웃만 반복해서 고르는 위치 편향이 생긴다. 섞어 주면 덱 전체의 레이아웃 다양성이 올라간다. 한 줄짜리 처방이지만 효과는 구조적이다.

질문 메모 상태 전이나 도구 입출력에서 막히는 부분을 적어두세요.

06sandbox와 finalize — 나머지 두 조각

sandbox: pptagent 서버는 파일을 모른다

앞의 표를 다시 보면 이상한 점이 있다. pptagent 서버의 도구 어디에도 “파일을 읽는다”가 없다. write_slide는 이미 완성된 텍스트와 이미지 경로를 받고, save_generated_slides만 파일을 하나 쓴다.

그럼 Research가 만들어 둔 manuscript.md는 누가 읽나? sandbox다. 그래서 PPTAgent 역할의 도구 목록에 sandbox가 함께 들어 있다. 둘은 역할이 깔끔하게 갈린다.

sandbox가 하는 일

  • 원고 manuscript.md 읽기
  • 첨부 이미지가 실제로 있는지 확인 (list_directory)
  • 표 이미지를 저장할 디렉터리 만들기
  • 필요하면 셸 명령 실행

pptagent가 하는 일

  • 템플릿 카탈로그 제공
  • 레이아웃 스키마 제공
  • 내용 검증
  • 슬라이드 렌더링과 pptx 저장

그리고 sandbox는 도커 컨테이너 안에서 돈다. 워크스페이스만 볼륨으로 붙고 (-v $HOST_WORKSPACE:$WORKSPACE -w $WORKSPACE), --rm으로 뜬다. LLM이 지어낸 셸 명령이 호스트에 직접 닿지 않게 하기 위한 격리다.

finalize: 종료 조건이자 품질 게이트

에이전트 루프는 “할 일 다 했다”는 모델의 말로는 끝나지 않는다. finalize 도구를 실제로 호출해야 끝난다 (deeppresenter/agents/pptagent.py:16-28). 그리고 그 도구는 역할마다 다른 계약을 검사한다 (deeppresenter/tools/task.py:58-111). 

elif agent_name == "PPTAgent":
    assert path.is_file() and path.suffix == ".pptx", \
        f"Outcome file should be a pptx file, got {path.suffix}"
    prs = Presentation(str(path))
    if len(prs.slides) <= 0:
        return "PPTX file should contain at least one slide"
숨은 인자: agent_name

이 분기는 agent_name 값에 달려 있는데, 그 인자는 @mcp.tool(exclude_args=["agent_name"])로 스키마에서 제외돼 있다. 즉 LLM은 이런 인자가 있다는 사실조차 모른다. 값은 프레임워크가 호출 직전에 몰래 끼워 넣는다: 

# deeppresenter/agents/agent.py:269-270
if t.function.name == "finalize":
    arguments["agent_name"] = self.name

덕분에 모델이 agent_name="Design"이라고 우겨서 pptx 검사를 우회하는 일이 원천적으로 불가능하다. 검증 기준을 피검증자의 손이 닿지 않는 곳에 둔 것이다.

질문 메모 이 부분에서 궁금한 점을 적어보세요.

07겹겹의 LLM — 도구 안에 또 모델이 있다

보통 MCP 서버는 “멍청한” 도구다. 파일을 읽고, 검색하고, 계산한다. pptagent 서버는 다르다. 자기 안에서 또 LLM을 부른다. 이게 이 시스템에서 가장 놓치기 쉬운 사실이고, 로컬 모델로 돌릴 때 병목의 정체이기도 하다.

호스트 프로세스 — PPTAgent 역할
LLM 호출 ① — research_agent 모델. 원고를 읽고 “generate_slide()를 부르겠다”는 도구 호출 JSON을 생성한다.
↓ stdio JSON-RPC
pptagent-mcp 프로세스 — PPTAgentServer.generate_slide()
_generate_commands() — 순수 파이썬. 템플릿 원본 내용과 새 내용을 비교해 (요소이름, 타입, quantity_change, 기존내용, 새내용) 튜플 목록을 만든다.
LLM 호출 ② — self.staffs["coder"]. 템플릿 슬라이드의 HTML 표현 + 위 명령 목록 + API 문서를 받아 실행 가능한 편집 코드를 생성한다. pptagent/pptgen.py:501-505
CodeExecutor.execute_actions() — 그 코드를 템플릿 슬라이드의 deepcopy에 실행한다. 실패하면 피드백을 붙여 retry_times만큼 재시도.
SlidePage 반환 → self.slides에 누적
이게 왜 중요한가

슬라이드 10장짜리 덱을 만들면 LLM 호출 ②만 최소 10번 일어난다. 바깥 에이전트의 호출 횟수와는 완전히 별개다. 게다가 이 안쪽 모델은 CONFIG_FILE의 research_agent 엔드포인트를 서버가 직접 다시 읽어 만든다 (pptagent/mcp_server.py:72-82). 로컬 Ollama처럼 동시 요청에 약한 백엔드라면, 여기서 큐가 쌓이면서 “generate_slide만 유난히 느리다”는 증상으로 나타난다.

서버 기동 시점의 연결 테스트

PPTAgentServer.__init__은 model.to_sync().test_connection()을 호출하고, 실패하면 예외를 던지며 죽는다. 그래서 모델 설정이 잘못돼 있으면 첫 도구 호출이 아니라 서버 기동 단계에서 무너진다. list_templates조차 못 부르는 상황이라면 도구 로직이 아니라 config.yaml을 먼저 의심해야 한다.

질문 메모 중첩 LLM 구조에서 헷갈리는 부분을 적어두세요.

08데이터는 실제로 어떻게 변형되는가

지금까지의 이야기를 장난감 데이터 하나로 관통해 보자. 원고의 한 페이지가 슬라이드 한 장이 되기까지 여섯 번 모습을 바꾼다.

① manuscript.md — Research 산출물

- 기존 방법은 텍스트 품질만 평가한다
- 시각적 완성도와 구조적 일관성은 빠져 있다

왜 ④ 같은 중간 표현을 거치는가

③에서 ⑤로 바로 갈 수도 있어 보인다. 하지만 그러면 coder LLM이 “원래 뭐가 있었고 몇 개를 지워야 하는지”를 스스로 추론해야 한다. ④는 그 차이 계산을 결정론적 파이썬으로 미리 끝내서 LLM에게는 “이 명령대로 코드만 써라”라는 훨씬 좁은 문제만 남긴다. LLM에게 맡기는 판단의 범위를 좁힐수록 실패율이 내려간다는 원칙이 여기 그대로 적용돼 있다.

09진입 경로의 함정

여기까지 읽고 터미널에서 템플릿 모드를 시험해 보려 한다면, 먼저 알아둘 게 있다. 지금 코드의 CLI로는 이 경로에 도달할 수 없다.

분기는 deeppresenter/main.py:141 한 줄이다. 

if request.convert_type == ConvertType.PPTAGENT:
    self.pptagent = PPTAgent(...)      # ← 이 글이 다룬 템플릿 경로
else:
    self.designagent = Design(...)     # ← 자유형 HTML 슬라이드 경로

그런데 convert_type의 기본값은 DEEPPRESENTER이고 (deeppresenter/utils/typings.py:187), CLI의 generate 명령은 InputRequest를 만들 때 이 필드를 아예 건드리지 않는다 (deeppresenter/cli/commands.py:356-362). 값을 넣어 주는 곳은 웹 UI뿐이다. 

# webui.py:33-34
CONVERT_MAPPING = {
    "自由生成 (freeform)": ConvertType.DEEPPRESENTER,
    "模版 (templates)":    ConvertType.PPTAGENT,
}
정리하면

pptagent generate …로는 항상 자유형(HTML) 경로를 탄다. 템플릿 기반 생성을 쓰려면 python webui.py로 웹 UI를 띄우고 출력 유형 드롭다운에서 模版 (templates)를 골라야 한다. 템플릿 이름 드롭다운은 그때만 나타나며, auto로 두면 template=None이 되어 모델이 list_templates 결과를 보고 직접 고른다.

CLI에 --mode template 같은 플래그를 붙이는 건 어렵지 않다 — generate()에 옵션 하나를 추가해 InputRequest(convert_type=…)에 넘기면 끝이다. 지금 없는 건 기술적 제약이 아니라 그냥 노출되지 않은 것뿐이다.

질문 메모 진입 경로나 설정에 대해 궁금한 점을 적어두세요.

10퀴즈

다섯 문제다. 답을 고르면 바로 채점되고 해설이 붙는다.

1. Research 역할의 도구 목록에서 pptagent 서버를 제외하는 가장 큰 이유는?

정답. set_template()은 self.slides.clear()를 실행한다. 상태를 가진 서버를 잘못된 단계에 노출하면 조용히 결과가 날아간다. 토큰 절약은 부수 효과일 뿐 설계 이유가 아니다.
아니다. 핵심은 상태다. pptagent 서버는 템플릿 컨텍스트와 누적 슬라이드를 프로세스 메모리에 들고 있어서, set_template이 한 번 잘못 호출되면 그때까지 만든 슬라이드가 전부 사라진다. 참고로 Research와 PPTAgent는 같은 research_agent 모델을 쓴다.

2. finalize의 agent_name 인자는 어떻게 채워지는가?

정답. @mcp.tool(exclude_args=["agent_name"])로 스키마에서 빠지고, agent.py:269-270에서 arguments["agent_name"] = self.name으로 주입된다. 모델이 검증 분기를 스스로 고를 수 없게 만든 설계다.
아니다. LLM은 이 인자의 존재조차 모른다 — exclude_args로 스키마에서 제거되기 때문이다. 값은 agent.py:269-270에서 프레임워크가 넣는다. 검증 기준을 피검증자가 건드릴 수 없게 하려는 의도다.

3. write_slide에 권장 글자수를 크게 초과하는 텍스트를 넘기면?

정답. mcp_slide_validate는 길이 문제를 warning으로 분류한다. 예외가 되는 건 요소 이름 불일치와 존재하지 않는 이미지 경로뿐이다. 응답 문구도 “고쳐 보되 5번 재시도 후에는 진행하라”는 협상형이다.
아니다. 길이 초과는 warning이라 예외를 던지지 않는다. error가 되는 경우는 두 가지 — 레이아웃에 없는 요소 이름을 썼거나, data에 넣은 이미지 파일이 실제로 존재하지 않을 때다.

4. 슬라이드 10장을 만들 때, pptagent MCP 서버 프로세스 안에서 일어나는 LLM 호출은 최소 몇 번인가?

정답. generate_slide → _edit_slide → self.staffs["coder"]가 매번 편집 코드를 생성한다. 바깥 에이전트의 호출과는 별개이고, 실패 시 재시도까지 붙는다. 로컬 모델에서 이 단계가 병목이 되는 이유다.
아니다. 이 서버는 “멍청한” 도구가 아니다. generate_slide가 불릴 때마다 내부 coder 역할 LLM이 편집 코드를 생성한다(pptgen.py:501). 10장이면 최소 10번, 재시도가 붙으면 그 이상이다.

5. pptagent generate "회사 소개" -o deck.pptx를 실행하면 어떤 경로를 타는가?

정답. convert_type 기본값은 DEEPPRESENTER이고 CLI는 이 필드를 설정하지 않는다. 템플릿 모드는 webui.py의 출력 유형 드롭다운으로만 들어갈 수 있다.
아니다. main.py:141의 분기는 convert_type 하나만 본다. 기본값은 DEEPPRESENTER(자유형)이고, CLI의 generate는 이 값을 건드리지 않는다. 첨부 파일이나 config.yaml은 이 분기에 영향을 주지 않는다.
질문 메모 틀린 문제가 있다면 무엇이 헷갈렸는지 적어두세요.

11정리

원본 문서가 “템플릿에서 슬라이드를 어떻게 뽑아내는가”라는 알고리즘의 문제를 다뤘다면, 이 글은 “그 알고리즘을 누가 운전하는가”라는 배선의 문제를 다뤘다. 요점은 다섯 가지다.

도구 격리
서버 7개를 한 번 띄우고, 역할마다 YAML로 다른 부분집합을 쥐어준다. Research는 pptagent를 못 본다.
상태 기계
pptagent 서버의 어서션들이 곧 상태 전이 규칙이다. 순서를 어기면 에러 문장이 LLM에게 되돌아간다.
역할 분담
pptagent는 파일을 모르고, sandbox는 슬라이드를 모른다. 겹치는 책임이 없다.
중첩 LLM
generate_slide 한 번이 MCP 서버 안에서 또 한 번의 LLM 호출을 부른다.
검증의 위치
finalize의 agent_name은 모델이 볼 수 없는 곳에서 주입된다. 게이트는 통과 대상이 열 수 없어야 한다.

마지막으로 다시 강조하면, 이 모든 흐름은 웹 UI에서 “模版 (templates)”를 골랐을 때만 실행된다. CLI로 같은 걸 하고 싶다면 generate()에 옵션 하나를 붙이는 게 가장 작은 변경이다.
