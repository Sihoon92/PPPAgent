01배경 — 슬라이드는 왜 “생성”하기 어려운가

발표자료를 자동으로 만들라는 요구는 겉보기에 텍스트 생성 문제처럼 보인다. 문서를 넣으면 슬라이드가 나온다. 그런데 슬라이드는 글이 아니라 배치된 도형들이다. 제목이 어디에 놓이고, 글머리 기호가 몇 개까지 들어가야 넘치지 않고, 로고가 왼쪽 아래 몇 pt 지점에 있어야 하는지 — 이 전부가 “내용”과 무관하게 미리 정해져 있어야 사람이 보기에 그럴듯하다. LLM에게 “예쁜 슬라이드를 만들어”라고 시키면 내용은 잘 쓰지만 배치는 무너진다.

깊은 배경 — .pptx가 실제로 무엇인지 (이미 아신다면 건너뛰세요)

.pptx 파일은 사실 ZIP 압축된 XML 묶음이다. 압축을 풀면 슬라이드 한 장마다 slide1.xml 같은 파일이 있고, 그 안에는 도형(shape)들이 좌표·크기·글꼴·색과 함께 적혀 있다. 이미지는 media/ 폴더에 실제 파일로 들어 있고 XML은 그걸 참조한다.

중요한 구조가 두 가지 더 있다.

  • 슬라이드 마스터 / 레이아웃: “제목 슬라이드”, “제목+내용” 같은 틀이 파일 안에 따로 저장되어 있다. 각 슬라이드는 “나는 이 레이아웃을 쓴다”라고 가리킨다. 테마 색, 기본 글꼴, 배경 그래픽이 여기 들어 있다.
  • 텍스트 프레임 / 문단 / 런(run): 텍스트 상자 하나 안에 문단(paragraph)이 여러 개 있고, 문단 하나 안에 서식이 같은 조각(run)이 여러 개 있다. “굵은 글씨 한 단어”는 별도의 run이다.

파이썬에서는 python-pptx(이 저장소는 포크인 pptagent_pptx를 쓴다)로 이 구조를 읽고 쓴다. 다만 이 라이브러리는 기존 도형을 수정하는 데는 강하지만, 보기 좋은 새 배치를 창조하지는 못한다. 좌표를 직접 계산해서 도형을 새로 놓으면 결과는 대개 처참하다.

그래서 이 프로젝트의 근본 전제가 나온다. 새로 그리지 말고, 잘 만들어진 슬라이드를 복제해서 내용만 바꾼다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

이 저장소의 두 스택

저장소를 열면 비슷한 개념이 두 군데에 있어 헷갈린다. AGENTS.md가 정리해 주는 대로 나누면 이렇다.

deeppresenter/
현재 제품 표면. CLI, 멀티 에이전트 루프, HTML→PPTX 변환 파이프라인. 오늘의 주제는 아니다.
pptagent/
이 글의 주제. 템플릿 기반 생성의 핵심 라이브러리. MCP 서버 pptagent-mcp의 실체이기도 하다.

그리고 pptagent/ 안은 다시 두 단계로 나뉜다. 코드의 docstring이 직접 이렇게 부른다.

Stage I · 오프라인 Presentation Analysis induct.py · 참조 PPTX 한 개를 뜯어서 레이아웃 카탈로그를 만든다. 템플릿당 딱 한 번.
→
저장물 slide_induction.json 카탈로그가 디스크에 남는다. 이후 생성은 이 파일만 읽는다.
→
Stage II · 요청마다 Presentation Generation pptgen.py · 카탈로그에서 레이아웃을 고르고 내용을 채워 새 덱을 만든다.

질문하신 세 가지가 정확히 이 그림에 대응한다. “템플릿 정보를 어떻게 저장하는가”는 Stage I의 결과물, “그걸로 어떻게 슬라이드를 만드는가”는 Stage II, “LLM이 어디에 쓰이는가”는 두 단계에 걸쳐 있다.

02직관 — 쓰지 말고 갈아끼워라

핵심 아이디어는 한 문장으로 요약된다.

핵심 발상

잘 만들어진 슬라이드 한 장은 “내용이 채워진 빈 칸들”이다. 그렇다면 그 슬라이드를 통째로 복제한 뒤, 각 빈 칸의 문단 텍스트만 새 내용으로 바꾸면 디자인은 원본 그대로면서 내용은 완전히 새로운 슬라이드가 된다.

아래 그림에서 이 발상을 시각적으로 보자. 이 글 전체에서 슬라이드는 이런 카드로 그린다: 초록 막대 = 제목, 회색 막대 = 텍스트 문단, 빗금 상자 = 이미지, 주황 테두리 = 기능성 슬라이드.

제목 문단 본문 문단 이미지 기능성 슬라이드

    data: ["이 페이지의 제목..."] },

오른쪽 카드에 회색 막대가 하나 늘어난 걸 눈치채셨는지. 원본은 항목 4개였는데 새 내용은 5개다. 그럴 땐 문단을 복제한다 — 새로 만드는 게 아니라, 기존 문단의 XML을 그대로 복사해서 붙이므로 글꼴·색·글머리 기호·들여쓰기가 전부 따라온다. 이것이 “갈아끼우기”가 “새로 그리기”보다 훨씬 안전한 이유다.

그런데 왜 “카탈로그”가 필요한가

참조 덱에 슬라이드가 30장 있다고 하자. 새 발표자료를 만들 때 30장을 다 쓰지는 않는다. 그중에는 본질적으로 같은 배치가 여러 번 반복되기도 한다 — 예를 들어 “제목 + 왼쪽 글머리 + 오른쪽 그림” 형태가 5번 나올 수 있다. 그렇다면 그 5장을 하나의 레이아웃으로 묶고, 대표 한 장만 골라 두면 된다.

layout: "Bullet list on left, screenshot on right:image" — slides [6, 11, 14], template_id = 11
6
11
대표 (도형 수 최다)
14

그래서 Stage I이 하는 일은 결국 “이 덱에는 몇 종류의 배치가 있고, 각 배치의 대표는 몇 번 슬라이드이며, 그 배치에는 어떤 빈 칸이 있는가”를 알아내 JSON으로 적어 두는 것이다. 이것이 카탈로그다.

03템플릿은 정확히 어떻게 저장되는가

템플릿 하나는 디렉터리 하나다. 데이터베이스도, 임베딩 인덱스도 없다. 그냥 폴더다. pptagent/templates/ 아래에 현재 여섯 개가 들어 있다: beamer, cip, default, hit, thu, ucas.

  • 📁 pptagent/templates/beamer/
    • 📄 source.pptx — 참조 발표자료 원본. 실제 슬라이드가 여기서 복제된다.
    • 📄 slide_induction.json — 레이아웃 카탈로그. 이 글의 주인공.
    • 📄 image_stats.json — 이미지별 크기·등장 횟수·VLM 캡션
    • 📁 images/ — 추출된 이미지 파일 (SHA1 파일명)
    • 📄 description.txt — 사람이 쓴 한 문단 설명. LLM에게 템플릿을 고르라고 보여줄 때 쓴다.

description.txt는 정말 그냥 산문이다. beamer 템플릿의 전문은 이렇다: 

A LaTeX Beamer-style template suitable for academic presentations, technical
talks, and conferences. Uses typical Beamer layout and typography for slides
with equations, figures, and structured sections.

MCP 서버의 list_templates 도구가 이 문장들을 그대로 모아 LLM에게 반환한다. 템플릿 선택은 임베딩 검색이 아니라 “설명 읽고 골라”다.

slide_induction.json — 카탈로그의 실제 모양

이 파일이 템플릿 저장의 핵심이다. 최상위는 평평한 dict이고, 키는 세 종류가 섞여 있다.

키 종류예시값
기능성 레이아웃
(고정 4종 중 존재하는 것)		 "opening", "table of contents",
"section outline", "ending"		 레이아웃 객체
내용 레이아웃
(개수 가변)		 "Labeled Diagram on Left with Explanatory Paragraph on Right:image" 레이아웃 객체
메타 키 2개 "functional_keys" / "language" ["opening", ...] / {"lid": "zh"}
내용 레이아웃 키의 문법: "<배치 설명문>:<text|image>"

콜론 앞은 비전 모델이 렌더된 슬라이드 그림을 보고 지어낸 한 줄 배치 설명이고, 콜론 뒤는 코드가 기계적으로 붙인 접미사다 — SlidePage.get_content_type()이 Picture 도형 존재 여부만 보고 "image" / "text"를 반환한다 (presentation/presentation.py:182). 이 접미사가 나중에 “그림 있는 슬라이드용 레이아웃 목록”과 “글만 있는 레이아웃 목록”을 가르는 유일한 기준이 된다.

실제 파일 일부다 (templates/beamer/slide_induction.json): 

{
  "opening": {
    "slides": [1],
    "template_id": 1,
    "elements": [
      { "name": "presenters and department", "type": "text",
        "data": ["潘伟洲(josephpan)", "SNG-社交平台部-空间运营中心 "] },
      { "name": "date",       "type": "text", "data": ["2025/4/30"] },
      { "name": "main title", "type": "text", "data": ["移动客户端通道面试陈述"] }
    ]
  },

  "Labeled Diagram on Left with Explanatory Paragraph on Right:image": {
    "template_id": 3,
    "slides": [3],
    "elements": [

      { "name": "main image",     "type": "image",
        "data": ["Diagram: Illustration of a coordinate system showing a tilted angle θ…"] }

  "functional_keys": ["opening", "table of contents", "ending"],
  "language": { "lid": "zh" }

레이아웃 객체의 필드는 이게 전부다:

template_id
1부터 시작하는 슬라이드 번호. 이 레이아웃을 쓸 때 source.pptx의 몇 번째 슬라이드를 복제할지.
slides
이 레이아웃으로 묶인 슬라이드 번호들. 생성 시에는 쓰이지 않고 분석 흔적으로 남는다.
elements[]
빈 칸 목록. 각 원소는 {name, type, data}.

element의 data가 “원본 내용”인 이유

처음 보면 이상하다. 왜 카탈로그에 원본 슬라이드의 실제 문구가 그대로 들어 있는가? 빈 칸 정의라면 이름과 타입만 있으면 될 것 같은데.

세 가지 용도가 있고, 셋 다 생성 단계에서 결정적이다.

  1. 길이 예산. 런타임 모델 Element(presentation/layout.py:29)는 로드 시 suggested_characters = max(len(i) for i in self.data)를 계산한다. “여기에 들어갈 텍스트는 대략 이 길이여야 안 넘친다”는 값이 JSON에 저장되지 않고 매번 원본 문구에서 유도된다.
  2. 이미지 캡션 = 이미지 슬롯의 정체성. 이미지 element의 data는 파일 경로가 아니라 캡션 문장이다. image_stats.json에 저장된 VLM 캡션이 여기 복사되어 있다. 나중에 편집 명령을 만들 때 “원래 있던 그림(=이 캡션)을 새 그림으로 교체하라”는 뜻으로 쓰인다.
  3. 편집 명령의 “before”. 생성 시 만들어지는 명령 튜플이 (이름, 타입, 수량변화, old_content, new_content) 형태인데, 이 old_content가 바로 여기의 data다. 코더 LLM은 슬라이드 HTML에서 이 문구를 찾아 어느 <p>를 건드릴지 판단한다.
저장되지 않는 것

좌표, 글꼴, 색, 도형 ID는 JSON에 없다. 그 정보는 전부 source.pptx 안에 그대로 있고, 생성 시 그 슬라이드를 복제하는 것으로 자동 따라온다. JSON은 “어느 슬라이드를 복제하고, 그 안의 어떤 문단들이 의미상 무엇인가”만 기록한다. 카탈로그가 4~8KB밖에 안 되는 이유다.

image_stats.json

{
  "1df5f510a94dff77293458473e5407d97a31bdfe.png": {
    "size": [784, 878],
    "appear_times": 1,
    "slide_numbers": [3],
    "relative_area": 33.96,
    "top_ranges_str": "3",
    "caption": "Diagram: Illustration of a coordinate system showing a tilted
                angle θ, with a yellow disk representing a cross-section…"
  }
}

파일명은 이미지 바이트의 SHA1이다 — 같은 그림이 여러 슬라이드에 있어도 파일은 하나로 합쳐진다. caption만이 LLM이 생성한 값이고 나머지는 계산값이다. 로드 시 ImageLabler.apply_stats()가 이 캡션을 메모리상의 Picture 객체에 다시 붙인다 (multimodal.py:32). 캡션 없이는 슬라이드를 HTML로 직렬화할 때 Picture.to_html이 예외를 던지므로, 이 파일은 선택 사항이 아니다.

스키마에는 있지만 이 저장소의 템플릿에는 없는 필드

Element에는 variable_length, variable_data가, Layout에는 vary_mapping이 정의되어 있다. “글머리 3개짜리와 5개짜리는 아예 다른 원본 슬라이드를 복제한다”는 기능이다. 하지만 현재 저장소에서 이 필드를 채워 넣는 코드는 없고 (induct.py가 생성하지 않는다), 여섯 템플릿 JSON 어디에도 등장하지 않는다. Layout.index_template_slide의 해당 분기는 사실상 죽은 경로다.

1단계 — 기능성 슬라이드 분리 (category_split)

입력은 덱 전체를 텍스트로 편 것이다. Presentation.to_text()가 "Slide 3 of 9\nTitle:…\n본문…\n----\n" 형태로 이어붙인 문자열을 만든다. 프롬프트는 prompts/category_split.txt이고, 찾을 범주를 정확히 네 개로 못박는다. 

출력 예:
{
  "opening": [1],
  "table of contents": [2],
  "section outline": [3, 7],
  "ending": [12]
}

코드는 이 결과를 뒤집어서 언급되지 않은 모든 슬라이드 번호를 “내용 슬라이드”로 삼는다 (induct.py:107). 기능성 슬라이드는 군집화를 거치지 않고 곧바로 레이아웃이 된다 — 클러스터의 첫 슬라이드가 template_id가 된다.

2단계 — 내용 슬라이드 군집화 (layout_split)

여기가 가장 영리한 부분이다. 문제는 이것이다: “배치가 같다”를 어떻게 기계가 판단하는가? 슬라이드 이미지를 그대로 비교하면 내용이 비슷한 것끼리 묶인다 — 우리가 원하는 건 그 반대다.

해법은 슬라이드를 두 벌 렌더링하는 것이다.

ppt_image_folder ← source.pptx
진짜 내용이 보이는 렌더

쓰임: 비전 모델에게 “이 배치를 뭐라 부를까?” 물을 때. 진짜 그림이 보여야 설명이 정확하다.

template_image_folder ← template.pptx
글자는 aaa…, 그림은 placeholder

쓰임: 임베딩 · 군집화. 내용이 지워졌으니 남은 유사도는 순수하게 배치 유사도다.

두 번째 벌은 Presentation.save(path, layout_only=True)가 만든다. clear_images()가 모든 그림 경로를 resource/pic_placeholder.png로 바꾸고, clear_text()가 모든 run의 텍스트를 "a" * len(원문)으로 치환한다 (presentation/presentation.py:408–422). 길이는 보존되므로 텍스트 블록의 크기감은 유지된다. 그다음 LibreOffice로 JPG를 뽑고, ViT (google/vit-base-patch16-224-in21k)로 임베딩한다.

군집화 자체는 두 겹이다.

거친 버킷 (slide_layout_name, content_type) PPTX가 이미 알려주는 “레이아웃 이름” + 그림 유무로 먼저 나눈다. 공짜 신호다.
→
버킷 안에서 코사인 유사도 → get_cluster(sim_bound=0.65) 평균 연결 방식으로 탐욕적 병합. 0.65 미만이면 각자 독립 클러스터.
→
대표 선정 max(len(slide.shapes)) 도형이 가장 많은 슬라이드를 template_id로. 가장 풍부한 예시를 고르는 것.
→
비전 LLM ask_category 대표의 진짜 렌더 이미지 1장 → 한 줄 배치 설명
왜 “도형이 가장 많은” 슬라이드를 대표로 뽑는가

빈 칸이 5개인 레이아웃은 3개만 채워서도 쓸 수 있지만, 빈 칸이 3개인 레이아웃에 5개를 채울 수는 없다. 가장 요소가 많은 슬라이드를 대표로 삼아야 표현력의 상한을 잃지 않는다.

ask_category.txt 프롬프트는 노골적으로 내용을 말하지 말라고 지시한다: “HOW content is structured에 집중하고, 구체적 주제나 내용 설명은 피하라.” 그래서 나오는 출력이 "Two Landscape Images with Descriptive Text Below Each" 같은 문장이다. 여기에 ":" + content_type을 붙여 최종 키가 된다.

질문 메모 두 벌 렌더링 그림에서 헷갈리는 점이 있으면 여기에.

3단계 — 스키마 추출 (content_induct)

이제 레이아웃마다 대표 슬라이드가 정해졌다. 마지막으로 그 슬라이드의 빈 칸에 이름을 붙인다.

입력은 슬라이드를 HTML로 직렬화한 것이다. SlidePage.to_html()이 만드는 형태는 이렇다 — 좌표와 글꼴이 인라인 스타일로, 문단은 <p id='n'>로, 그림은 <img alt='캡션'>로: 

<div id="0" style="font-size: 32pt; top: 50pt; left: 100pt; width: 500pt; font-weight: bold;">
  <p id="0">个人经历</p>
</div>
<div id="1" style="font-size: 14pt; top: 150pt; left: 600pt; width: 300pt;">
  <p id="0">这张图展示了一个倾斜圆盘在空间中的几何关系…</p>
</div>
<img id="2" alt="Diagram: Illustration of a coordinate system showing a tilted angle θ…"/>

schema_extractor 에이전트(roles/schema_extractor.yaml)가 이걸 받아 element 목록을 뱉는다. 프롬프트는 이름을 지을 때 역할과 위치를 쓰라고 지시한다: “section/main/sub title”, “left/right bullets”, “portrait/landscape image”, “slide/section number” 등. 그래서 "main title", "explanation bullets", "slide number" 같은 이름이 나온다.

중요한 안전장치 — LLM이 내용을 지어내지 못하게 막는 법

스키마 추출은 내용을 새로 쓰는 작업이 아니라 분류 작업이다. 그런데 LLM은 중국어 원문을 옮겨 적다가 오타를 내거나 요약해 버리기 쉽다. 이 코드는 그걸 타입 시스템 수준에서 막는다 (response/induct.py): 

_allowed_contents = ContextVar("allowed_contents")

class SlideElement(BaseModel):
    name: str
    data: list[str]
    type: Literal["text", "image"]

    def model_post_init(self, _):
        # LLM이 뭘 적었든, 허용된 원본 문자열 중 가장 가까운 것으로 스냅
        self.data = [
            max(_allowed_contents.get(), key=lambda x: edit_distance(x, d))
            for d in self.data
        ]

허용 목록은 호출 측에서 [모든 문단 텍스트] + [모든 그림 캡션]으로 세팅된다 (induct.py:190). 결과적으로 data는 반드시 원본에 실재하는 문자열이 된다. LLM이 결정하는 건 오직 이름과 그룹핑뿐이다.

마지막으로 language_id()가 fastText lid.176 모델로 언어 코드를 뽑아 {"lid": "zh"}를 붙이면 카탈로그가 완성되고, JSON으로 저장된다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

05저장된 템플릿으로 슬라이드를 만드는 과정 (Stage II)

이제 반대 방향이다. 카탈로그와 source.pptx가 주어졌을 때 새 슬라이드는 어떻게 나오는가.

준비: set_reference()

pptgen.py:90의 이 메서드가 JSON을 살아 있는 객체로 바꾼다. 

self.reference_lang    = Language(**slide_induction.pop("language"))     # {"lid": "zh"}
self.functional_layouts = slide_induction.pop("functional_keys")         # ["opening", ...]
self.layouts = {k: Layout(title=k, **v) for k, v in slide_induction.items()}

self.text_layouts       = [k for k in self.layouts if k.endswith("text")  and k not in functional]
self.multimodal_layouts = [k for k in self.layouts if not k.endswith("text") and k not in functional]

주목할 두 가지가 있다.

첫째, empty_prs는 “빈 덱”이 아니라 원본의 깊은 복사본이다. Presentation.__post_init__이 원본 파일을 다시 열어 slide_layouts 매핑을 만들어 두므로, 이 객체는 테마·마스터·글꼴 정의를 전부 지닌 채 슬라이드 목록만 갈아끼울 수 있는 껍데기다. 마지막에 empty_prs.slides = 생성된_슬라이드들을 대입하고 save()하면, clear_slides()가 기존 슬라이드를 다 떼어내고 새 슬라이드를 각자의 원래 레이아웃 위에 다시 짓는다.

둘째, _hide_small_pics(0.2)가 실행된다. 슬라이드 면적의 20% 미만인 그림 — 로고, 장식용 아이콘 — 은 shapes에서 빠져 backgrounds로 옮겨지고, 레이아웃의 element 목록에서도 제거된다. 채워야 할 슬롯이 아니라 배경의 일부로 취급하는 것이다. 그 결과 어떤 레이아웃의 그림이 전부 사라지면 키의 :image가 :text로 바뀐다 (pptgen.py:340).

_generate_commands는 레이아웃 쪽 element 전체를 순회하며, editor 출력에 없는 이름은 new_content = []로 둔다. 그러면 quantity_change가 음수가 되어 그 문단들은 삭제 명령이 된다. 즉 “안 쓰는 슬롯은 지워라”가 자동으로 표현된다.

⑤ coder — 명령을 실제 API 호출로

coder 에이전트에 세 가지가 들어간다:

api_docs
CodeExecutor.get_apis_docs()가 inspect로 실제 함수 시그니처와 docstring을 뽑아 만든 문서. 쓸 수 있는 함수는 5개뿐: replace_paragraph, clone_paragraph, del_paragraph, replace_image, del_image.
edit_target
대표 슬라이드의 HTML. div id와 p id가 곧 API 인자다.
command_list
위에서 만든 튜플들을 문자열로 이어붙인 것.

출력은 JSON이 아니라 파이썬 호출문 여러 줄이다:

# ("main title", "text", "quantity_change: 0", [...], ["RAG 파이프라인 개요"])
replace_paragraph(0, 0, "RAG 파이프라인 개요")

# ("main bullets", "text", "quantity_change: 1", [...4개...], [...5개...])
clone_paragraph(1, 3)   # 새 paragraph_id 는 현재 최대(3) + 1 = 4
replace_paragraph(1, 0, "문서를 청크로 분할")
replace_paragraph(1, 1, "임베딩 후 벡터 DB 저장")
replace_paragraph(1, 2, "질의와 유사한 청크 검색")
replace_paragraph(1, 3, "LLM 프롬프트에 삽입")
replace_paragraph(1, 4, "답변 생성")

첫 인자 0, 1은 HTML의 div id, 둘째 인자는 그 안의 p id다. LLM이 element 이름과 도형 ID를 잇는 다리 역할을 하는 셈이다.

⑥ 실행 — 그리고 “지연된 편집”

CodeExecutor.execute_actions()가 한 줄씩 eval한다. 안전장치가 몇 겹 있다:

  • SAFE_EVAL_GLOBALS = {"__builtins__": {}} — 내장 함수 접근 차단.
  • 등록된 5개 함수 외 호출은 SlideEditError.
  • def로 시작하는 줄(함수 정의) 금지.
  • 한 명령 블록 안에서 clone_*과 del_*을 섞으면 거부 — 수량 변화 방향이 하나여야 한다.

그런데 여기서 가장 중요한 설계는 따로 있다. API 함수들은 실제 PPTX를 즉시 고치지 않는다. 예를 들어 replace_paragraph는 가벼운 Paragraph 객체의 텍스트를 바꾸고, 동시에 클로저를 큐에 쌓는다(apis.py:403): 

para.text = text
shape._closures[ClosureType.REPLACE].append(
    Closure(partial(replace_para, para.real_idx, text), para.real_idx)
)
para.edited = True

이 클로저는 나중에 SlidePage.build()에서 진짜 python-pptx 도형에 대해 실행된다. 그때서야 마크다운을 파싱해 **굵게**를 별도 run으로 쪼개고, 하이퍼링크를 달고, 서식을 유지한 채 텍스트를 쓴다. 편집을 “의도의 목록”으로 미뤄 두었다가 마지막에 한 번에 적용하는 것 — 그래서 재시도가 깨끗하다.

재시도가 오염되지 않는 이유

_edit_slide의 재시도 루프는 매 시도마다 edit_slide = deepcopy(self.presentation.slides[template_id - 1])로 템플릿 슬라이드를 처음부터 다시 복사한다 (pptgen.py:508). 앞선 시도에서 절반쯤 적용된 상태가 남지 않는다. 실패 시 coder에게 넘기는 피드백은 오류 줄에 --> Error Line: 표시를 박은 코드 전문 + traceback이다.

마지막 청소: validate()

LLM이 어떤 문단을 그냥 잊어버렸다면? 그 문단에는 원본 템플릿의 중국어 문구가 그대로 남아 있을 것이다. Presentation.validate()가 이걸 막는다(presentation/presentation.py:378): 

for shape in slide:
    for para in shape.text_frame.paragraphs:
        if not para.edited and para.idx != -1:
            shape._closures[ClosureType.POST_PROCESS].append(
                Closure(partial(del_para, para.real_idx), para.real_idx)
            )

edited 플래그가 찍히지 않은 문단은 전부 삭제된다. 잔재가 새어 나올 여지를 원천 봉쇄하는, 단순하고 무자비한 규칙이다.

덱 전체로 확장하기

generate_pres()는 개요(outline)의 항목마다 위 과정을 asyncio.gather로 동시에 돌린다. 슬라이드 간 의존이 없기 때문에 가능하다 (max_at_once로 세마포어를 걸 수 있다).

기능성 슬라이드는 개요 생성 후 규칙 기반으로 끼워 넣는다(_add_functional_layouts). 목차는 0번 위치, 표지는 그 앞, 마무리는 끝, 섹션 표지는 주제가 바뀌는 지점마다. 이때 카탈로그의 기능성 키 이름과 표준 이름을 edit_distance > 0.7로 매칭하므로, 템플릿에 해당 레이아웃이 없으면 그냥 건너뛴다.

질문 메모 명령 목록 → API 호출 → 클로저 흐름에서 막히는 부분을 적어 두세요.

06LLM은 어디에서, 무엇을 받고 무엇을 뱉는가

지금까지 LLM 호출이 산발적으로 등장했으니 한자리에 모아 보자. 이 시스템에서 LLM 호출은 전부 Agent 클래스(pptagent/agent.py:55)를 거친다. 에이전트 하나는 roles/<이름>.yaml 파일 하나에 대응하고, 그 YAML에는 system_prompt, Jinja2 template, 필수 인자 목록 jinja_args, 쓸 모델 종류 use_model(language/vision), return_json이 들어 있다.

인자 누락은 조용히 넘어가지 않는다

Agent.__call__은 assert self.prompt_args == set(jinja_args.keys())로 정확히 일치를 요구하고, Jinja 환경은 StrictUndefined다. 프롬프트에 빈 칸이 남은 채 모델로 나가는 일이 구조적으로 불가능하다.

구조적 출력이 이 시스템을 지탱한다

표에서 “Literal[…]로 제약”이라고 적은 부분들이 이 코드베이스의 특징적인 기법이다. 프롬프트로 “있는 레이아웃 중에서만 골라”라고 부탁하는 대신, pydantic 모델을 런타임에 만들어 다른 값을 낼 수 없게 한다 (response/pptgen.py): 

class LayoutChoice(BaseModel):
    reasoning: str
    layout: str

    @classmethod
    def response_model(cls, layouts: list[str]):
        return create_model(
            cls.__name__,
            reasoning=(str, Field(...)),
            layout=(Literal[*layouts], Field(...)),   # ← 여기
            __base__=BaseModel,
        )

같은 기법이 세 군데 더 쓰인다:

EditorOutput
element name이 그 레이아웃의 실제 element 이름만 될 수 있다.
OutlineItem
indexes의 섹션/서브섹션 제목이 문서에 실재하는 제목만, images가 실재하는 이미지 경로만 될 수 있다. (이미지가 하나도 없으면 Literal 대신 str로 두고, model_post_init이 목록을 비운다.)
SlideSchema
앞서 본 edit_distance 스냅. Literal이 아니라 사후 보정이지만 목적은 같다.

Literal로 막을 수 없는 것 — 이미지 경로처럼 값이 길고 오타가 잦은 것 — 은 사후 스냅으로 처리한다. Layout.validate()는 editor가 적은 이미지 경로를 허용된 경로 중 가장 가까운 것으로 바꾸되, 유사도가 0.5 미만이거나 파일이 실제로 없으면 예외를 던진다(presentation/layout.py:77). 예외가 나면 editor.retry()로 되돌아간다.

길이 제어 — length_factor

템플릿의 suggested_characters는 원본 언어 기준이다. 중국어 16자짜리 제목 자리에 영어로 16자를 쓰면 텅 비어 보인다. 그래서 언어 계열을 비교해 배수를 정한다 (pptgen.py:39):

원본 → 목표배수이유
같은 계열 (CJK→CJK, 라틴→라틴)1.2약간의 여유만
라틴 → CJK0.7한자는 정보 밀도가 높아 글자 수가 준다
CJK → 라틴2.0반대로 늘어난다

CJK 판정은 단순하다 — lid in ["zh", "ja", "ko"]. 한국어로 생성하면 zh 템플릿과 같은 계열이므로 1.2배다. 어떤 element의 최장 문자열이 suggested_characters × length_factor를 5자 넘게 초과하면 length_rewrite LLM 호출이 발동해 그 배열만 다시 줄인다. 프롬프트는 “출력 배열의 길이는 입력과 같아야 한다”고 못박아, 줄이다가 항목이 사라지는 사고를 막는다.

질문 메모 LLM 호출 표나 구조적 출력에 대해 궁금한 점을 적어보세요.

07두 개의 실행 경로: 자동 파이프라인 vs MCP 도구

지금까지 설명한 Stage II에는 사실 두 가지 진입점이 있고, 둘은 “LLM 호출을 누가 하느냐”가 다르다.

경로 A — PPTAgent (pptgen.py)

문서(Document) 하나를 통째로 받아 덱 전체를 한 번에 만든다. planner → content_organizer → layout_selector → editor → coder 다섯 역할이 모두 코드 안에서 자동으로 호출된다. 호출자는 그냥 generate_pres(source_doc, num_slides=12)를 기다리면 된다.

경로 B — PPTAgentServer (mcp_server.py)

이쪽은 외부 에이전트(Claude, Cursor, 혹은 deeppresenter의 PPTAgent 역할)가 MCP 도구를 하나씩 호출하며 직접 운전한다. 그래서 roles = ["coder"] — 내부 역할이 coder 하나로 줄어든다. 계획·내용 조직·레이아웃 선택·내용 작성은 전부 바깥 에이전트의 머리로 옮겨간 것이다.

toollist_templates()이름 + description.txt 반환
→
toolset_template(name)set_reference() 실행 → available_layouts 반환
→
toolcreate_slide(layout)content_schema 문자열 반환
→
toolwrite_slide(elements)검증 → errors면 예외, warnings면 경고 반환
→
toolgenerate_slide()coder 실행 → SlidePage 축적
→
toolsave_generated_slides(path).pptx 파일로 저장

create_slide가 돌려주는 content_schema는 사람이 읽을 수 있는 평문이다 (presentation/layout.py:132). 예: 

Element: main title
	type: text
	suggested_characters: 16
	The default quantity of the element is 1
Element: main bullets
	type: text
	suggested_characters: 66
	The default quantity of the element is 4

외부 에이전트는 이걸 읽고 write_slide에 [{"name": ..., "data": [...]}]를 넘긴다. 경로 A에서 editor LLM이 하던 일을 여기서는 호출하는 쪽 에이전트가 하는 것이다. 검증도 조금 다르다 — mcp_slide_validate는 길이 초과를 예외가 아니라 경고로 돌려주고 “5번까지 고쳐 보라”고 문장으로 안내한다. 대화형 도구답게 실패 대신 협상을 택한 것이다.

MCP 경로의 길이 기준은 영어 고정

mcp_slide_validate는 get_length_factor(prs_lang, Language.english())를 쓴다. 실제 생성 언어가 무엇이든 목표 언어를 영어로 가정한다는 뜻이다. 중국어 템플릿이면 배수가 2.0이 되어, 한국어로 쓸 때는 사실상 상당히 헐거운 상한이 된다.

표 처리도 이 경로의 특징이다. 슬라이드에 표를 넣고 싶으면 마크다운 표를 그대로 넣을 수 없고, markdown_table_to_image(markdown_table, path, css)로 이미지를 만든 뒤 그 경로를 이미지 element의 data로 넣어야 한다. deeppresenter/roles/PPTAgent.yaml의 시스템 프롬프트가 이 규칙을 명시적으로 가르친다.

08날카로운 모서리

코드를 읽다 보면 눈에 걸리는 지점들이 있다. 실제로 부딪힐 수 있는 것들만 정리한다.

set_reference()는 입력 dict를 파괴한다

slide_induction.pop("language")와 pop("functional_keys")는 기본값이 없다. 그런데 MCP 서버는 self.templates[name]["slide_induction"]을 복사 없이 넘긴다 (mcp_server.py:193). 따라서 한 프로세스에서 set_template을 두 번 호출하면 두 번째에 KeyError: 'language'가 난다. save_generated_slides가 _initialized = False로 되돌리므로, 서버 한 번 띄워서 덱 두 개를 만드는 흐름은 현재 코드로는 성립하지 않는다.

content_induct의 zip은 키 순서에 의존한다

zip(layout_induction.keys(), schemas)에서 keys()에는 "functional_keys"도 들어 있지만 schemas에는 없다(루프에서 건너뛰므로). 파이썬 dict의 삽입 순서 보장 덕분에 "functional_keys"가 마지막에 들어가고 zip이 짧은 쪽에서 멈춰 우연히 맞는다. 누군가 이 키를 먼저 넣도록 바꾸면 스키마가 엉뚱한 레이아웃에 붙는다. 같은 함수의 if "content_schema" in cluster 조건도 실제로 저장되는 키는 "elements"라 항상 거짓이다.

언어 판정은 슬라이드 한 장으로만 한다

layout_induction["language"] = language_id(slide.to_text())의 slide는 바로 위 for 루프에서 새어 나온 변수 — 즉 마지막으로 순회한 레이아웃의 대표 슬라이드 하나다 (induct.py:208). 다국어가 섞인 덱이면 결과가 흔들릴 수 있다.

템플릿을 새로 추가하려면

필요한 것은 다섯 가지다: source.pptx, images/, image_stats.json, slide_induction.json, description.txt. 앞의 넷은 scripts/template_induct.py가 만들어 주지만, 그 스크립트는 LibreOffice(렌더링), ViT(임베딩, GPU 권장), 언어·비전 LLM을 모두 요구한다. description.txt만은 사람이 직접 써야 한다. 참조 덱을 준비하는 요령은 pptagent/BESTPRACTICE.md에 정리되어 있다 — 슬라이드당 요소 6개 이하, 텍스트 프레임은 “넘치면 자동 축소”, 표지와 마무리 슬라이드는 반드시 포함, 같은 층위의 내용은 하나의 요소 안 글머리로 (별도 텍스트 상자로 쪼개지 말 것).

10정리

세 질문에 대한 한 문단짜리 답으로 마무리한다.

어떻게 저장하는가
폴더 하나. source.pptx(디자인의 실체) + slide_induction.json(레이아웃 카탈로그) + image_stats.json·images/(그림과 캡션) + description.txt(사람이 쓴 소개). 카탈로그에는 좌표도 색도 없다 — “어느 슬라이드를 복제할지(template_id)”와 “그 안의 문단들이 각각 무엇인지(elements)”뿐이다.
어떻게 생성하는가
레이아웃을 고르고 → 각 element에 넣을 문자열 배열을 만들고 → 원본 대비 수량 변화를 포함한 명령 목록으로 바꾸고 → LLM이 그것을 5개짜리 편집 API 호출로 번역하고 → 템플릿 슬라이드의 깊은 복사본 위에서 실행한다. 실제 PPTX 수정은 클로저로 미뤄 두었다가 빌드 시점에 한꺼번에 적용되고, 손대지 않은 문단은 전부 삭제된다.
LLM은 어디에
템플릿 분석에 4곳(캡션·기능성 분류·배치 명명·스키마 추출), 생성에 최대 6곳(계획·요점정리·레이아웃 선택·내용 작성·길이 축약·코드 생성). 거의 모든 출력이 pydantic Literal로 제약되거나 edit_distance로 원본에 스냅되어, LLM은 “창작”이 아니라 주어진 선택지 안에서의 판단을 하도록 좁혀져 있다. MCP 경로에서는 이 중 앞의 넷이 외부 에이전트에게 위임되고 coder만 서버 안에 남는다.
